## 接口规范

### 统一响应格式

#### 当前 Node.js 版本
```json
{
  "success": true,
  "data": {},
  "error": "错误信息（失败时）"
}
```

#### 建议 Java 版本（可选）
```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

### 统一状态码

| HTTP 状态码 | code | 说明 |
|------------|------|------|
| 200 | 0 | 请求成功 |
| 400 | 400 | 参数错误 |
| 401 | 401 | 未授权（未登录或 token 失效） |
| 403 | 403 | 无权限 |
| 404 | 404 | 资源不存在 |
| 409 | 409 | 冲突（如资源已存在） |
| 500 | 500 | 服务器内部错误 |

### 统一分页参数

| 参数名 | 类型 | 必填 | 默认值 | 说明 |
|--------|------|------|--------|------|
| page | number | 否 | 1 | 页码，从1开始 |
| pageSize | number | 否 | 20 | 每页数量 |

### 统一分页响应

```json
{
  "list": [],
  "total": 100,
  "page": 1,
  "pageSize": 20
}
```

## 认证和鉴权

### 当前实现（Node.js）
- 暂无认证机制（原型阶段）

### 建议实现（Java）
- **认证方式**：JWT Token
- **请求头**：`Authorization: Bearer {token}`
- **Token 有效期**：7天
- **Token 刷新**：提供 refresh token 机制

## 开发规范

### 接口文档规范

所有接口文档必须包含以下内容：

1. **基本信息**
   - 接口路径
   - 请求方式（GET/POST/PUT/DELETE/PATCH）
   - 接口说明
   - 权限要求
   - 开发状态（已实现/待开发）

2. **请求参数**
   - 参数名、类型、必填、说明、示例
   - 区分 Query 参数、Body 参数、路径参数

3. **响应数据**
   - 成功响应示例
   - 响应字段说明
   - 错误响应示例

4. **业务逻辑**
   - 核心业务逻辑说明
   - 特殊处理情况
   - 数据校验规则

5. **前端对接**
   - TypeScript 类型定义
   - Service 函数实现
   - 使用示例

6. **测试用例**
   - 正常场景
   - 异常场景

### 接口命名规范

| 操作 | 请求方式 | 路径示例 | 说明 |
|------|---------|---------|------|
| 获取列表 | GET | `/api/resources` | 查询列表，支持分页和筛选 |
| 获取详情 | GET | `/api/resources/{id}` | 查询单个资源 |
| 创建 | POST | `/api/resources` 或 `/api/resources/create` | 创建新资源 |
| 更新 | PUT | `/api/resources/{id}` | 完整更新资源 |
| 部分更新 | PATCH | `/api/resources/{id}` | 部分更新资源 |
| 删除 | DELETE | `/api/resources/{id}` | 删除资源 |
| 批量操作 | POST | `/api/resources/batch` | 批量创建/更新/删除 |
| 特殊操作 | POST | `/api/resources/{id}/action` | 如复制、发布、归档 |

## 常见问题

### Q1: Node.js 和 Java 版本的响应格式不一致怎么办？
A: 前端已实现统一的 axios 拦截器，会自动适配不同的响应格式。

### Q2: 为什么有些接口标记为"待开发"？
A: 这些接口是基于业务需求规划的扩展功能，当前 Node.js 版本只实现了核心功能。

### Q3: Java 后端开发时是否必须遵循现有接口路径？
A: 建议保持一致以减少前端改动，但如果有更好的设计，可以与前端协商调整。

### Q4: 如何测试接口？
A: 推荐使用 Postman 或 Apifox，可以从文档中复制请求示例进行测试。
